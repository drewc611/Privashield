# Development Guide

## Prerequisites

- Git
- Python 3.12 or newer (the project will not install on 3.11)
- Docker Engine or Docker Desktop with Compose v2, to run the full stack
- Node.js, only for the dashboard syntax check
- [uv](https://docs.astral.sh/uv/), optional, used by `make lock` and to create
  the virtualenv faster than `venv`
- a local Ollama-compatible runtime for AI-enabled development, optional for
  core ingestion work

Linux is the reference platform for network sensors and future enforcement.
Backend and UI development stay possible on macOS and Windows where privileged
networking is not required.

## Getting started

```sh
make install        # create .venv on Python 3.12 and install with dev tooling
make hooks          # install the git pre-commit hooks
make verify         # run every gate CI runs
```

`make install` builds an isolated `.venv/`, so it does not matter which Python
happens to be on your `PATH`. Every other target uses that virtualenv. Run
`make help` for the full list.

To run the API alone against in-memory storage:

```sh
make run            # http://127.0.0.1:8000, docs at /docs
```

To run the whole stack, including PostgreSQL, NATS and the dashboard:

```sh
cp .env.example .env
make up             # or ./scripts/install.sh
```

## Repository layout

```text
apps/
  api/            FastAPI control plane (privashield_api)
  dashboard/      static operator dashboard served by nginx
services/
  collector/      Suricata and Zeek log collector (privashield_collector)
  file-monitor/   host filesystem monitor (privashield_file_monitor)
evaluation/       detection corpus and regression thresholds
scripts/          policy signing and installation helpers
tests/            pytest suite covering all three packages
docs/             architecture, operations and governance documentation
requirements/     hash-pinned lockfiles, generated by `make lock`
```

An asynchronous worker, shared domain packages and a migrations tree are
described in `ARCHITECTURE.md` as future work. They do not exist yet; do not
document them here as though they do.

## Dependency management

Runtime and development dependencies are declared as version ranges in
`pyproject.toml` and resolved into hash-pinned lockfiles under `requirements/`.
CI installs from those lockfiles with `--require-hashes`, so a build is
reproducible and every artifact is verified against a recorded digest.

After changing a dependency in `pyproject.toml`:

```sh
make lock           # regenerate requirements/runtime.txt and requirements/dev.txt
```

CI runs `pip check` against the lockfile and fails if `pyproject.toml` declares
something the lockfile does not carry, which is what a forgotten `make lock`
looks like.

To reproduce CI's exact dependency set locally:

```sh
make install-locked
```

## Quality gates

`make verify` runs the same checks as CI, in the same order:

| Target                | Checks                                                |
| --------------------- | ----------------------------------------------------- |
| `make governance`     | agent policy, harness and CODEOWNERS consistency       |
| `make lint`           | `ruff format --check` and `ruff check`                 |
| `make typecheck`      | `mypy` over apps, services, scripts and tests          |
| `make test`           | pytest with branch coverage against the coverage floor |
| `make benchmark`      | detection regression corpus against committed thresholds |
| `make check-dashboard`| dashboard JavaScript syntax                            |
| `make check-compose`  | Compose file validity                                  |

If `make verify` passes locally, CI passes. Run `make format` to apply
formatting and safe lint fixes before committing, or let the pre-commit hooks
do it.

Coverage is enforced as a floor, not a target. It may not drop. When you raise
it, raise `COVERAGE_MIN` in the `Makefile` to match so it cannot slip back.

Type checking is on for the whole tree. `privashield_api.database` carries a
documented mypy override for its ORM-to-Pydantic conversions; narrow it as
those conversions are made explicit, rather than adding new exclusions.

## Python standards

- type annotations on public and service-layer interfaces, checked by mypy
- Pydantic for external contracts
- SQLAlchemy for persistence
- formatting and linting enforced in CI
- no arbitrary shell execution from request or model data
- dependency injection around transports, storage, clocks, model providers and
  enforcement backends, so they can be substituted in tests

## Dashboard standards

The dashboard is intentionally dependency-free: hand-written HTML, CSS and
JavaScript served as static files by nginx. There is no build step and no
package manager. Keep it that way unless the complexity genuinely warrants a
toolchain, and raise it as an ADR if it does.

- no rendering of untrusted telemetry or model output as raw HTML
- accessible keyboard and navigation behavior for operator controls
- high-impact actions require clear state and confirmation

## Configuration

Configuration is layered:

1. safe code defaults
2. configuration file and environment overrides
3. persisted operator configuration for approved runtime settings
4. secret references kept outside ordinary configuration responses

Do not introduce undocumented environment variables. `.env.example` is the
reference.

## Database schema

The API currently creates its schema at startup from the SQLAlchemy metadata.
This is a Phase 1 bootstrap, marked as such in `privashield_api/database.py`,
and is not safe for an upgrade path with existing data. Explicit migrations are
required before any deployment that must survive a schema change; when they
land, every schema change goes through them and destructive changes require
backup and restore validation.

## Feature flags and modes

Risky features use explicit capability flags or operating modes. `observe` is
the default for new detection and enforcement integrations until acceptance
tests justify stronger behavior.

## Test data

Use synthetic or sanitized fixtures. Do not commit real credentials, customer
logs, PHI, private packet captures, or other sensitive data. The
`detect-private-key` pre-commit hook catches the most obvious mistakes, but it
is not a substitute for care.

## Documentation

Update docs in the same PR when behavior, API, schema, deployment, security
assumptions, or failure modes change.
